# ADR-001 Authentication and Identity Model

**Status:** Approved
**Date:** 11 June 2026
**Supersedes:** None
**Related:** ADR-000 Foundation Decisions

---

# Context

Watchtower requires a secure, scalable authentication model that supports:

* Individual users
* Team workspaces
* Future enterprise customers
* Future MFA adoption
* Future Single Sign-On (SSO)
* Future passkey support

The authentication solution must minimise custom security code while supporting rapid product development.

---

# Decision

Watchtower will use Supabase Auth as the authentication provider.

Authentication logic will not be custom built.

Supabase will be responsible for:

* User accounts
* Password hashing
* Email verification
* Password reset
* Session management
* MFA capability
* Passkey capability
* Future SSO integration

Watchtower will be responsible for:

* User profiles
* Workspace membership
* Roles and permissions
* Audit logging
* Feature access

---

# User Registration Flow

A new user will:

1. Enter email address
2. Enter password
3. Submit registration

System actions:

1. Create Supabase Auth account
2. Send verification email
3. Create application profile
4. Create default personal workspace
5. Assign Owner role
6. Create workspace settings
7. Create initial audit log entries

Users may not access protected platform areas until their email address has been verified.

---

# User Login Flow

User enters:

* Email address
* Password

System validates credentials through Supabase Auth.

Successful login creates a valid authenticated session.

Failed logins must not reveal whether the email address exists.

---

# Email Verification

Email verification is mandatory.

Users must verify their email address before accessing protected Watchtower functionality.

The platform should provide:

* Verification email
* Resend verification email
* Verification success page
* Verification failure page

---

# Password Reset

Users must be able to request a password reset.

The reset process will be managed through Supabase Auth.

Watchtower will not generate or manage password reset tokens directly.

---

# Password Policy

## Requirements

Minimum password length:

15 characters

Maximum password length:

128 characters

Passwords may contain:

* Letters
* Numbers
* Symbols
* Spaces

Passwords generated by password managers must be supported.

Browser-generated passwords must be supported.

Paste must be allowed.

Autofill must be supported.

---

## Not Required

The platform will not require:

* Uppercase characters
* Lowercase characters
* Numbers
* Symbols
* Regular password changes

Password quality should be driven primarily by length and uniqueness.

---

# Profile Creation

Upon successful registration:

A profile record will be created.

Fields include:

* id
* email
* display_name

Display name will initially be derived from the email address.

Example:

[mark.nesbit@example.com](mailto:mark.nesbit@example.com)

becomes:

Mark Nesbit

---

# Display Name Governance

Display names are controlled through workspace policy.

The capability to restrict editing exists from day one.

The governing rule will be configurable through workspace settings rather than hardcoded into authentication logic.

---

# Workspace Creation

Every user receives a default workspace during onboarding.

Example:

Display Name:

Mark Nesbit

Workspace:

Mark Nesbit Workspace

Database type:

personal

The user receives the Owner role within that workspace.

---

# Session Management

Authentication sessions are managed by Supabase.

Watchtower will not create custom session infrastructure.

Protected routes must require a valid authenticated session.

Unauthenticated users are redirected to login.

---

# Multi-Factor Authentication (MFA)

MFA is not required for MVP.

The platform must be designed so MFA can be enabled later without schema redesign.

The following capabilities are anticipated:

* Time-based One-Time Passwords (TOTP)
* Authenticator applications
* Recovery codes

Workspace-level policies may require MFA in future releases.

---

# Passkeys

Passkeys are not required for MVP.

Authentication architecture must not prevent future passkey adoption.

---

# Single Sign-On (SSO)

SSO is not required for MVP.

The authentication architecture must support future integration with:

* Microsoft Entra ID
* Google Workspace
* Generic SAML providers
* OpenID Connect providers

SSO is expected to become a paid or enterprise capability.

---

# Audit Requirements

The following events must be logged:

* User registration
* Email verification
* Login
* Logout
* Password reset request
* Password reset completion
* Workspace creation

Audit events should include:

* Timestamp
* User identifier
* Event type
* Workspace identifier where applicable

---

# Security Principles

Authentication security should prioritise:

1. Proven authentication services
2. Minimal custom security code
3. Email verification
4. Strong password support
5. Future MFA support
6. Auditability

---

# Consequences

Benefits:

* Reduced security implementation risk
* Faster development
* Future enterprise compatibility
* Simplified maintenance
* Strong authentication baseline

Trade-offs:

* Dependency on Supabase Auth
* Some future authentication features depend on Supabase capabilities

This trade-off is considered acceptable for MVP and early growth.
